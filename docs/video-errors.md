# Video render failures: one vocabulary

A video render can fail in about a dozen ways. Each is now named once, where it is detected, as
a `RenderErrorKind` (`backend/services/job_types.py`). Every surface reads the same record:

- the batch status JSON;
- the MCP and chat tools;
- the Studio Video Gen page;
- the Jobs page;
- the music-video and Film Crew pipelines.

`RENDER_ERROR_POLICY`, next to the enum, holds per kind the label, the next step to show, and
whether a retry can help.

## The record

A failed clip in `/api/batch-video/status/<id>` carries `error` (the message, as before),
`error_kind`, and `failure`:

```json
{"kind": "oom", "label": "Out of GPU memory",
 "message": "ComfyUI ran out of GPU memory in KSamplerAdvanced (node 10): Allocation on device",
 "action": "Lower the size, length or steps, or turn off upscale and LoRAs.",
 "retryable": false, "retry_after_s": []}
```

The batch itself gets `failure`: its own error (VRAM wait, capacity, cancel, a crashed worker),
else the first failed clip's. A refused request (HTTP 400 from `/generate/text` or
`/generate/image`) carries the same record under `error.details.failure`.

Who reads it:

- **MCP / chat.** `get_generation_status` prints each failure as `Failed item: <label>:
  <message> Next: <action>`, with the records in its metadata. `generate_video` returns the same
  line as its error.
- **Studio.** The result card shows the label, the message and the next step
  (`components/videogen/RenderFailureNote.jsx`). A refused queue request shows its record.
- **Jobs page.** `error_message` is the same line, and `metadata.failure` is the record.
- **Pipelines.** Music video and the Film Crew I2V wrappers raise `render_failed(what, kind,
  message)`: "Wan 2.2 I2V failed — Out of GPU memory: … Next: …". The kind rides on the exception
  (`classify_render_exception`).

## Failure points

"Before" is what each surface got before this change.

| Kind | Detected in | Before | Now |
|---|---|---|---|
| `invalid_request` | `preflight_video_model` (unknown model), `render_limits.start_image`, speed profile / adapter / style-embedding / reference checks, withheld style, unsupported model | the message, no kind | same message, kind |
| `model_not_installed` | preflight ("is not installed"); a ComfyUI `/prompt` refusal whose loader `*_name` value is `value_not_in_list`; LTX 2.5 / CogVideoX I2V file checks | preflight: 400 with the message. `/prompt`: "Failed to queue workflow in ComfyUI: Prompt outputs failed validation — Value not in list: …" | kind; the refusal is recognised as a missing file |
| `companion_missing` | preflight ("missing companion"); a speed-profile LoRA, an adapter or a user text encoder not installed | the message | kind, marked where the check fails |
| `comfyui_down` | ComfyUI unreachable before the render, the router finding no backend, a failed `--reserve-vram` restart, ComfyUI gone during the render, a failed upload to an unreachable ComfyUI | **mid-render: "ComfyUI generation timed out or failed".** **With the cached flag still set, "ComfyUI is missing the VHS_VideoCombine node … run install_deps.sh"**: wrong advice | "ComfyUI stopped answering during the render" / "ComfyUI is not answering, so its nodes could not be checked" |
| `node_missing` | VHS or ComfyUI-GGUF missing from `/object_info` (ComfyUI reachable); a `/prompt` refusal of type `missing_node_type` | refusal: "Failed to queue workflow in ComfyUI: Node 'X' not found…" | kind |
| `card_too_small` | `_vram_preflight` (model needs more than the card); `GpuCapacityError` at batch admission | the message | kind |
| `vram_busy` | `_ensure_vram_for_model` wait ran out; the batch GPU-admission deadline | the message | kind; retryable |
| `oom` | ComfyUI `execution_error` with an out-of-memory exception type; an OOM raised in this process | **inside ComfyUI: "ComfyUI generation timed out or failed"** (F-25); in-process: an OOM message | "ComfyUI ran out of GPU memory in <node> (node <id>): <first line>" |
| `node_error` | any other ComfyUI `execution_error`; other `/prompt` validation refusals | **"ComfyUI generation timed out or failed"** | "ComfyUI failed in <node> (node <id>): <first line>" |
| `render_timeout` | the wait's hard ceiling; a prompt that leaves the queue without a result | "ComfyUI generation timed out or failed" | which of the two, and after how long; retryable |
| `blank_output` | the zero-placebo guard: a stub file, or a clip black for its whole length | the message. **Without an `ffmpeg` binary the black check was skipped** and a black clip counted as success | kind. Without `ffmpeg`, PyAV decides whether every sampled frame is black |
| `output_missing` | ComfyUI finished but no file downloaded; a cast keyframe that never came | "No files were generated by ComfyUI" | kind; retryable |
| `cancelled` | ComfyUI `execution_interrupted`; cancel before start, while waiting for the GPU, or by the user | interrupt: **"ComfyUI generation timed out or failed"** | kind |
| `unknown` | any other exception | the exception text | kind, same text |

The MCP `get_generation_status` still returns success for a failed batch: the status query itself
succeeded. Its text and metadata now say which kind of failure it was and what to do. Before, it
listed raw error strings.

## Retries

`RENDER_ERROR_POLICY[kind]["retry_after_s"]` is the wait before each retry, and its length is the
attempt budget. Only these kinds are retryable:

| Kind | Waits (s) |
|---|---|
| `comfyui_down` | 30 |
| `vram_busy` | 60, 180 |
| `render_timeout` | 60 |
| `output_missing` | 30 |

The waits are starting values, not measurements. ComfyUI comes back in about 5 s on a warm box,
and a batch holding the card usually ends within minutes.

`GUAARDVARK_VIDEO_AUTO_RETRY=1` (off by default) makes the batch worker render such a clip again
after those waits. Each attempt starts from a fresh copy of the request, so the prompt is enhanced
once per attempt. The result records `render_attempts`. With the setting off, a clip renders once,
as before. The GPU-admission loop in `_run_batch` keeps its own backoff.

## Not covered

- **The offline diffusers backend** (`offline_video_generator.py`) returns plain errors; its
  failures read as `unknown` unless they are an OOM. F-27 (success without an MP4 when muxing
  fails) is unchanged.
- **Music video and Film Crew** carry the kind in the text they raise. Their database rows keep a
  message, not a separate kind field.
