# backend/constraints.txt — global pip CONSTRAINTS for the shared backend venv.
#
# Applied via PIP_CONSTRAINT by start.sh's bootstrap passes,
# scripts/heal_backend_venv.sh, scripts/install_pytorch.sh and
# plugins/comfyui/scripts/install_deps.sh (guarded: only when this file exists
# and PIP_CONSTRAINT isn't already set by the caller). Constraints never ADD
# packages — they only cap versions when pip resolves something anyway.
#
# WHY: two layers re-resolve numpy independently of requirements.txt and used
# to drag it off the ML stack's line on every install (Observed in the 24.04
# client box setup.log: numpy flip-flopped between the torch pass and the
# repin steps, re-staging torch each boot):
#   1. install_pytorch.sh's `pip install --upgrade --force-reinstall torch...`
#      re-resolves numpy from the pytorch index (which hosts 2.0.0-2.5.2 cp312
#      manylinux x86_64 on cu124/cu128/cpu — verified 2026-09-02).
#   2. ComfyUI custom-node requirements installed into this same venv.
# With these constraints the resolver picks a compliant version up front; the
# repin steps (scripts/lib/venv_pins.sh) stay as no-op belt-and-braces.
#
# NOTE for isolated plugin venvs (scripts/dep_reconciler/reconcilers/
# isolated_plugin_venv.py): NOT applied there on purpose — those venvs manage
# their own stacks and may legitimately want numpy 2.x.

numpy>=2.1,<2.6  # ceiling follows numba (0.67.0 declares numpy<2.6); the torch pass re-resolves numpy from the PyTorch index where numba is not in the graph. Measured 2.5.2, 2026-09-02

# OpenCV: the three distributions (opencv-python, -headless, -contrib) unpack
# into ONE cv2/ directory and the last one installed wins. Different versions
# of two of them in the same venv leave a cv2 that imports but does not match
# either package's metadata (observed here 2026-09-02: opencv-python 4.8.1.78
# beside -headless/-contrib 5.0.0.93, pip check failing on both). Lock every
# name to the same version so whichever a dependency asks for, the files agree.
# 5.0.0.93 is the first line built against numpy 2 with an open numpy ceiling
# (4.12.0.88 declares numpy<2.3, which fights numba's 2.5.x); it moves with the
# numpy line, never separately.
# These constraints are inert during the torch pass: opencv is not in torch's
# dependency graph, so the PyTorch index never has to serve it (see the
# setuptools note below for why that matters).
opencv-python==5.0.0.93
opencv-python-headless==5.0.0.93
opencv-contrib-python==5.0.0.93

# setuptools<81,>=80.9.0  -- REMOVED: unsatisfiable from the PyTorch index.
#   install_pytorch.sh installs with --index-url https://download.pytorch.org/whl/<ver>,
#   which REPLACES PyPI. That index hosts only setuptools 70.0.0/70.2.0/78.1.0, so this
#   pin made torch ResolutionImpossible on every fresh machine (no GPU support at all).
#   start.sh already force-reinstalls setuptools>=80.9.0,<81 AFTER torch, so pinning it
#   here was redundant as well as fatal.
